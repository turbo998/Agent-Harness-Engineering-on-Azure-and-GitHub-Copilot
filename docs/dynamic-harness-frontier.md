# From Static to Dynamic Harness — and the Quarantine Pattern

> Source: Anthropic, *A harness for every task — Dynamic Workflows in Claude Code* — https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code
> Chinese commentary: https://mp.weixin.qq.com/s/hxBkT-iJleQkaODzjWVC2A

## 1. Where this Workshop sits: three pillars of *static* harness

The three pillars of this Workshop — **CCGS** (Claude Code in GitHub Spaces), **OpenShell**, and **GitHub Copilot** — are all, in Anthropic's new vocabulary, **static harnesses**. The orchestration graph is written by a human ahead of time:

- A `chatmode.md` file declares the role and tool budget of a single agent.
- A `prompt.md` file declares the steps of a single task.
- A `workflow.yml` file declares the DAG between jobs.

The graph is fixed at authoring time. The LLM gets to *fill in the blanks* (which file to edit, what code to write), but the *shape* of the orchestration — how many agents, who reviews whom, when to fan out — is decided by you, the harness author. This is the right default: it is auditable, repeatable, and constrains the blast radius.

## 2. Dynamic harness — the LLM writes the orchestration

The new idea in Opus 4.8's release blog is to let the LLM itself **emit a JavaScript orchestration script at run time**, and execute it. The script can call `agent()`, `parallel()`, `pipeline()` and friends; it can decide on the fly that this particular task needs 12 parallel workers and a 3-round tournament, while the next one needs a single agent and a `Loop-Until-Stable`. The harness is no longer a fixed file in the repo; it is a per-task artifact generated alongside the answer.

Why this matters: a static harness optimised for "review a PR" is terrible at "rewrite a runtime in Rust", and vice versa. The pre-Opus-4.8 workaround was to maintain a zoo of chatmodes and workflows; the dynamic-harness bet is that the model is now good enough to **design** the right harness on the spot, given a description of the task and the available primitives.

Key primitives:

- `agent({ system, input, tools })` — spawn a single sub-agent in a fresh context.
- `parallel([...promises])` — fan out.
- `pipeline([stepA, stepB, stepC])` — chain.

These three are enough to express all six orchestration patterns from the [previous doc](./six-orchestration-patterns.md).

## 3. Case study: Bun's Zig → Rust rewrite

The blog's headline example is the **Bun** team using Claude Code to drive a chunk of their Zig-to-Rust rewrite. The dynamic harness, generated by the model, did roughly:

1. **Fan-out by file / call site.** For each Zig source file, spawn an agent in its own git worktree (so concurrent edits never collide on the filesystem).
2. **Per-worker pipeline.** Each worker: read the Zig file → produce a Rust equivalent → run `cargo check` → iterate.
3. **Adversarial review.** A separate reviewer agent, with no access to the Zig original, reads only the Rust output and flags anything that looks unidiomatic or unsound.
4. **Reduce.** A final agent re-checks cross-file invariants (matching FFI signatures, shared types) and opens one PR per logical chunk.

Crucially the *number* of worktrees, the *depth* of the review loop, and even the decision to skip review for trivial files were emitted by the model based on the shape of the codebase. A static workflow author could not have predicted them all.

## 4. Case study: Cat Wu's A/B flag cleanup

Cat Wu (Anthropic) demoed a smaller but very GHCP-relevant case: cleaning up dead A/B feature flags. The dynamic harness:

1. Generated a query plan to find all flag references (ripgrep + LSP).
2. **Classify-routed** each call site: "flag is now always-on" → inline the true branch; "flag is now always-off" → delete the false branch; "ambiguous" → escalate to a separate human-review queue.
3. **Loop-Until-Stable** on the per-file edits until the typechecker was happy.
4. Generated a changelog by **reducing** the per-file diffs.

The harness here is short — maybe 40 lines of generated JS — but each stage uses one of the six patterns. The model didn't invent new patterns; it composed known ones.

## 5. Quarantine — isolation as an orchestration concern

The most security-relevant idea in the blog is **Quarantine**: when an agent reads untrusted content (a webpage, a PR description from a stranger, the output of an external API), that agent **must not** hold high-privilege tools. Only an agent that operates on a sanitised summary of the untrusted content is allowed to call dangerous APIs.

In an Azure enterprise context the mapping is direct:

- The **reader** agent has tools: `fetch`, `readFile`, `searchWeb`. It has **no** Azure Managed Identity. It reads the world, then emits a structured, sanitised summary (typed JSON, with prompt-injection sentinels stripped).
- The **executor** agent has tools: `arm.deploy`, `keyvault.getSecret`, `storage.write`. It is wired to a Managed Identity. It receives **only** the sanitised summary, never the raw external bytes. Its system prompt cannot be influenced by anything the reader saw.

This is layered defence:

| Layer | Mechanism | What it prevents |
|---|---|---|
| Infrastructure | `disableLocalAuth=true` + Managed Identity + RBAC scoping | Stolen credentials cannot be used; the only path to Azure is through identities the agent process holds. |
| Agent orchestration | Quarantine pattern (reader / executor split) | Prompt injection in untrusted content cannot reach the executor's tool calls, because the executor never sees the untrusted bytes. |

Both are necessary. Infrastructure-layer hardening alone does not stop a single all-powerful agent from being talked into `rm -rf` by a malicious README. Quarantine alone does not stop a leaked API key. The two compose.

## 6. Lab 3 wrap-up: adding the fourth pillar

In the Lab 3 closing slide we extend the Workshop's "three pillars" diagram with a **fourth column: Dynamic Harness**, and frame the progression as:

1. **Single-agent IDE assist** (legacy Copilot Chat) — no harness.
2. **Static chatmode / prompt-file harness** (Lab 1) — author writes the role split.
3. **Static workflow / multi-agent DAG** (Lab 2) — author writes the orchestration graph.
4. **Dynamic harness** (Lab 3 outlook) — model emits the orchestration graph; author writes the *primitives*, the *budget*, and the *quarantine boundaries*.

The author's job does not disappear — it shifts upward. You stop writing the workflow and start writing the **runtime that runs workflows**: what primitives exist, what tools each spawned agent may hold, where the trust boundaries are, what the maximum spend is. That is the harness-engineering skill set the next 12 months will reward, and it is exactly what this Workshop is preparing you for.
