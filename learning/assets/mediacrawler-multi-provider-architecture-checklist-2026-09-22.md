## 可迁移模式

| 历史阅读中观察到的结构 | 可复用的设计意图 | 反面风险 |
|---|---|---|
| 抽象 crawler/login/client/store，各 provider 独立目录 | 稳定契约与可替换实现分离 | 把单个 provider 的所有特殊能力强塞到统一接口 |
| provider code → 实现类的注册表 | 将选择逻辑集中，新增实现有固定接入点 | 未知 provider 静默回退到错误目标 |
| 浏览器态管理与异步请求客户端分离 | 重客户端管理交互、轻客户端处理受授权操作 | 凭据流向失控，或误以为有登录态就有调用权限 |
| 资源有效期检查与请求逻辑分离 | 将短期凭据或连接租约生命周期显式建模 | 各 provider 重复刷新、并发刷新风暴 |
| 异常类别决定重试 | 瞬时失败与永久业务错误有不同恢复策略 | 无限重试、重复扣款、对权限拒绝反复重放 |

注册表并不意味着「永远不用改现有代码」：新增适配通常仍需登记、配置与测试。是否使用插件发现机制，应由规模与安全边界决定，不提前泛化。

## 最小设计模板（无实现代码）

```text
contracts/   # 小而稳定的接口；输入/输出/异常约定
providers/   # 每个 provider 独立实现及其契约测试
registry/    # 明确允许列表；未知名称立即报错
lifecycle/   # 凭据/租约生命周期与刷新协调
policies/    # 授权、重试上限、幂等与速率限制
stores/      # 独立存储实现，不侵入 provider 主流程
```

认证信息只交给获授权的接收方；优先使用正式 SDK/API 与标准 token 交换机制。不得为了复用性能模式跨域复制浏览器 Cookie。浏览器方案是否存在，不改变访问授权要求。

## 编码前写下这些意图测试

- [ ] 同一契约测试能运行于两个无网络假 provider，输出结构一致。
- [ ] 不认识的 provider 名称立刻失败，绝不发送到默认 provider。
- [ ] provider A 的认证材料不会出现在 provider B 的请求或日志中。
- [ ] 到期租约在使用前刷新；并发请求不会无限重复刷新。
- [ ] 认证拒绝、目标不存在等永久错误不进入无上限重试。
- [ ] 暂时性网络失败受次数与总时长限制；取消信号可以停止等待。
- [ ] 非幂等写操作不因重试而产生重复副作用；无幂等保证时停止自动重试。
- [ ] 更换存储后端不需要修改 provider 业务流程。
