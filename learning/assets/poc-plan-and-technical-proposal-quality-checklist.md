# POC 计划 / 技术方案文档质量检查清单

> **用途**：SA 写 POC 部署计划、架构方案文档、RFC 时的自查清单——把"这份方案写得够不够好"从主观判断变成可勾选的门禁。改写自 `obra/superpowers` 的 `writing-plans`/`executing-plans`/`brainstorming` 方法论（"写计划给零上下文读者"范式 + "设计前置"纪律），从"给 subagent 的任务简报"场景移植到"给客户/团队的技术交付物"场景。
> **来源**：`obra/superpowers`（github.com/obra/superpowers，244k+★，2026-07-06 二次核实存活）`skills/writing-plans/SKILL.md` + `skills/executing-plans/SKILL.md` + `skills/brainstorming/SKILL.md`（2026-07-10 新增，raw.githubusercontent.com 均 200）。外部内容仅作方法论参考。
> **定位**：本文档讲“怎么写 POC 计划/方案文档”（面向人类评审与可能的 agent 落地），重点是让零上下文读者也能独立执行和审阅。

---

## 核心原则：假设读者是"零上下文但手艺不错的工程师/客户方技术负责人"

写方案文档时，默认对方**没有**参与过你脑内的所有讨论。每一处"我们之前聊过的"、"按惯例"、"你懂的"都是潜在的返工种子。

---

## 结构检查清单（逐项打钩）

### A. 文档头部（Header）必须包含

- [ ] **Goal** — 一句话讲清"做完是什么样子"（不是"怎么做"，是"完成态"）
- [ ] **Architecture** — 涉及哪些组件/服务，画一张图或列一张表
- [ ] **Tech Stack** — 具体版本号（Azure 服务 SKU、SDK 版本、模型版本）——不写"最新版"这种会过期的话
- [ ] **Global Constraints**（全局约束，逐条精确复制自客户需求/合规要求）——这些约束对下面所有任务隐式生效，写在头部一次，不要每个任务里重复一遍导致遗漏

### B. 每个任务/里程碑单元必须包含

- [ ] **Files/Resources**：创建什么、修改什么、怎么验证（Create/Modify/Test 三分类）
- [ ] **Interfaces: Consumes / Produces**——精确到"消费什么格式的输入、产出什么格式的输出"，不要只画一个箭头。（个人经验，非统计数据）不少架构图容易漏掉这层严谨性：每个组件应清楚标注接口契约，而非只有连线。
- [ ] **颗粒度**：单个任务应该小到"可独立验证、值得一次评审"（obra 原文给"2-5分钟一步"的参考量级，POC 语境可放宽到"半天一个可交付里程碑"，但仍要求**独立可验证**）
- [ ] 如果是给编码 agent 落地的任务，走 TDD 五步骤：写验证方法 → 确认现状不满足 → 最小实现 → 验证满足 → 提交

### C. 禁止项（No-Placeholder 铁律，逐项检查你的文档里有没有）

以下任意一条出现 = 该段落判定为"计划失败"，必须补全再交付：

- [ ] ❌ "TBD" / "待定"
- [ ] ❌ "添加适当的错误处理" / "add appropriate error handling"（适当=多少？哪种？obra 原文举的例子，此类空话是常见的方案文档硬伤之一）
- [ ] ❌ "类似 Task N 那样做"（省略重复内容——对 agent 执行者等于没写，对人类读者等于要翻页核对）
- [ ] ❌ "酌情调整" / "按需处理"
- [ ] ❌ 未注明版本号的"最新版 XX"
- [ ] ❌ 合规/安全类要求只写"确保安全"而不给具体控制项（哪层隔离、哪个角色、哪条策略）

### D. 交付前 Self-Review 三件套

1. **Spec 覆盖度扫描**：客户原始需求的每一条，能不能在文档里找到对应段落？漏了哪条？
2. **占位符扫描**：过一遍 C 节禁止项列表。
3. **跨任务一致性检查**：任务 A 里定义的接口名/参数名，任务 B 引用时是否完全一致？（obra 原文例子：Task3 叫 `clearLayers()` 但 Task7 写成 `clearFullLayers()` 就是 bug——同理，方案文档里"Agent 服务"和"Foundry Agent Service"如果指同一个东西，全文要统一措辞，不要让客户误以为是两个不同组件）

---

## 执行纪律（executing-plans 移植）：该停就停

- 执行计划（无论是人类还是 agent 执行）时，**遇到阻塞/看不懂指令/反复验证失败 → 立刻停下问人，不能瞎猜**。
- 环境支持 subagent/多 agent 编排时，优先用任务分解、独立执行和复核，而非让单一执行者从头做到尾。
- **"止损点"设计原则**：方案文档应显式标注"到这一步如果 XX 条件不满足，停下来找 SA/客户确认"的检查点，而不是假设执行者会自己判断该不该继续。

## SA 落点对照表

| 交付场景 | 用这份清单做什么 |
|---|---|
| **写 POC 部署计划** | 头部四件套（Goal/Architecture/Tech Stack/Global Constraints）确保客户一眼看懂范围边界；任务颗粒度按"半天一个可验证里程碑"拆分，避免"两周后才发现方向错了"。 |
| **技术方案文档 / RFC 评审** | 用 C 节禁止项列表扫一遍团队/自己写的文档，"添加适当的监控"这类空话是（个人经验）方案文档里常见的硬伤之一。 |
| **架构图配套说明** | Interfaces: Consumes/Produces 的思路直接套用到图上每条连线的标注——不要只画箭头，写清楚"经什么协议/什么格式"。 |
| **客户验收对齐** | Self-Review 三件套里的"Spec 覆盖度扫描"可以直接做成验收前的逐条对照表，配合 `eval-driven-improvement-loop-and-poc-acceptance-cheatsheet.md` 的执行式二元验证一起用。 |
| **止损纪律** | 遇到不确定先核实；验证反复失败时停止执行并确认阻塞原因。完成声明必须附可复现的验证证据。 |

## E. 写计划之前：需求澄清纪律（`brainstorming` skill 移植，2026-07-10 新增）

上面 A-D 节假设"要写的东西已经想清楚了"。但**方案文档写得再规范，如果需求本身没澄清清楚，一样返工**。这一节补的是"写计划之前"的阶段，来源同为 `obra/superpowers` 的姊妹 skill `brainstorming`（`raw.githubusercontent.com/obra/superpowers/main/skills/brainstorming/SKILL.md`，200 核实）：

- **硬性设计门禁**：无论客户需求听起来多简单，**没有先讨论清楚设计、拿到明确认可，就不要直接开始写详细方案或动手实现**——"看起来简单的需求"恰恰最容易因为跳过这一步而在后期返工（原文用于代码场景的 hard-gate，这里移植为"方案文档"场景：不要一收到需求就直接输出完整方案，先确认范围）。
- **一次只问一个澄清问题，优先选择题**：与客户对齐需求边界（合规、网络、预算、租户位置）时，避免一次抛出 5 个开放式问题让对方无从下手。批量相关问题时也要分组呈现，不要"审讯式"连续追问。
- **先给 2-3 个方案选项 + 权衡 + 推荐**，再展开细节——这与方案评审中的“选项对比 + 推荐方案”是同一心法，`brainstorming` skill 印证了“设计前置”这件事在独立信源里被反复验证的通用工程纪律。
- **范围识别与拆解**：如果客户需求里包含多个独立子系统/子问题，**立刻**标记出来，引导拆成多个独立的"设计→计划→实施"循环，而不是急着把一个过大范围的方案一次性写细——对应本文档 B 节"任务颗粒度"检查项的**上游**（先切对整体范围，再切每个任务）。
- **分段落展示设计、每段落单独确认**——大型方案文档避免一次性甩一整篇长文让客户消化不了，按逻辑段落（如"整体架构"→"数据流"→"安全边界"→"部署步骤"）分段呈现并逐段确认，比一次性输出全文再等一个笼统的"没问题"更能提前暴露理解偏差。

**三段论完整拼图**：`brainstorming`（需求澄清+方案选型，本节）→ `writing-plans`（把选定方案写成结构化计划，A-D 节）→ `executing-plans`（执行纪律，"执行纪律"节）——三个阶段对应同一份 `obra/superpowers` 方法论体系的三个连续 skill，本文档现在完整覆盖了 POC/方案文档生命周期的全部三段。

---



- **计划质量与执行验收分开检查**：先确认目标、接口、约束、步骤自包含，再用可执行的通过/失败标准验收实际产物；文档完整不等于部署已经验证。
