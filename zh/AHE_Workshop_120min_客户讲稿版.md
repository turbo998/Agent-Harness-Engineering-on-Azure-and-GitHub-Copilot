# GHCP Workshop 客户讲稿版（对应升级版 PPT）

> 用法建议：
> - 每页不需要逐字照读，按 3–5 句主线讲即可
> - 面向客户技术团队，语气建议：清晰、克制、偏工程化
> - 重点不是“AI 很神”，而是“AI 如何在工程流程里可控地发挥价值”

---

## Slide 1｜封面：GitHub Copilot 从 IDE 助手到 Agent 工作流

建议讲稿：

1. 今天这 120 分钟，我们不只是看 GitHub Copilot 怎么写几行代码，而是看它怎么从 IDE 辅助升级成一个可以参与开发闭环的 Agent。
2. 我们会从最熟悉的 IDE 使用开始，逐步走到 Ask、Plan、Agent 这条完整工作流。
3. 后半场会有 Demo 和动手实验，确保大家不是“听懂了”，而是真的能上手。
4. 今天的重点不是炫技，而是帮助大家判断：在真实团队里，什么任务适合用 Copilot，怎么用才稳。

---

## Slide 2｜Workshop 目标与学习成果

建议讲稿：

1. 今天的目标主要有三个：第一，理解 Copilot 从 IDE 助手到 Agent 的能力边界；第二，掌握 Ask、Plan、Agent 的典型用法；第三，亲手完成一次最小闭环实验。
2. 对技术团队来说，价值不在于“多快生成代码”，而在于能否减少上下文切换、提高执行效率，同时保留治理边界。
3. 所以今天我们会反复强调两个词：**生产力** 和 **可控性**。
4. 如果今天结束后，大家能知道什么时候该问、什么时候该先规划、什么时候该交给 Agent 执行，这场 workshop 就算达标了。

---

## Slide 3｜120 分钟议程

建议讲稿：

1. 前半段先把能力框架讲清楚，包括 IDE 主线、Agent 模式、审批与自治。
2. 中间会做一段 Live Demo，让大家看到 Ask 到 Agent 的完整闭环。
3. 后半段我们重点做三个实验：AI-DLC、Harness Engineering、Multi-Agent 协作。
4. 也就是说，今天不只是“会用”，还会讨论“怎么工程化落地”。

---

## Slide 4｜Part 1：从 IDE 助手到 Agent 工作流

建议讲稿：

1. 这一部分的核心是先建立一个共同认知：Copilot 不是一个孤立功能，而是一条工作流。
2. 如果只把它当成代码补全工具，它的价值其实只发挥了一部分。
3. 真正对技术团队更有意义的，是把它放回开发流程中去看：理解、规划、执行、验证。

---

## Slide 5｜GitHub Copilot 在技术团队中的三层价值

建议讲稿：

1. 我通常会把 Copilot 的价值分成三层：即时辅助、结构化协作、任务代理。
2. 第一层大家最熟悉，比如补全代码、解释代码、写测试样例。
3. 第二层开始进入协作阶段，也就是通过 Chat 和 Plan 先把问题想清楚。
4. 第三层才是 Agent 真正的价值：围绕一个目标跨文件推进任务，并且自己验证结果。
5. 所以今天 workshop 的主线，就是从“问问题”走向“交任务”。

---

## Slide 6｜IDE 使用主线：从理解到执行

建议讲稿：

1. 大家可以把 Copilot 在 IDE 里的使用方式，理解成一条从理解到执行的链路。
2. Ask 适合理解项目、找入口、分析错误；Inline 更适合局部补全和小范围修改。
3. Plan 的作用是先把任务边界锁清楚，尤其适合复杂一点但还不想立刻执行的需求。
4. Agent 则是执行层，负责跨文件改动、跑命令、补测试、做验证。
5. 最后一定要回到 terminal 和 review，把 AI 产出纳入现有工程流程。

---

## Slide 7｜Agent Mode 核心概念

建议讲稿：

1. Agent 和传统 Chat 最大的区别在于，它不是只回答你，而是能围绕目标主动推进。
2. 它会读代码、拆步骤、改文件、跑命令、看结果，再决定下一步怎么修正。
3. 所以它不是“更会聊天”，而是“更会执行”。
4. 这里 Ask、Plan、Agent 三种模式可以理解为三种控制粒度：Ask 最保守，Plan 先思考，Agent 最执行导向。
5. 真正成熟的使用方式，不是三选一，而是组合使用。

---

## Slide 8｜Agent 类型：local / CLI / cloud / third-party

建议讲稿：

1. 从落地角度看，可以先记住两个最核心差异：本地交互式，和后台执行式。
2. Local agent 更贴近 IDE，适合边聊边做、逐步推进。
3. CLI 或 cloud agent 更适合定义清楚的任务，让它在后台跑，你继续做别的事情。
4. 如果组织有模型、合规、平台方面的要求，也可以引入 third-party agents 或特定 harness。
5. 所以这里不是谁更高级，而是谁更适合当前任务场景。

---

## Slide 9｜审批与自治：如何安全地用 Agent

建议讲稿：

1. 对企业团队来说，最重要的问题不是“Agent 能不能改代码”，而是“它在什么边界内可以改”。
2. 我一般建议从默认审批开始，先在低风险、小范围任务里建立信心。
3. 随着规则越来越清楚、验证越来越完善，再逐步提高自治程度。
4. 这里的关键理念是：权限不是越高越好，而是要和任务风险匹配。
5. 所以每次交任务前，最好把范围、约束和验收标准说清楚。

---

## Slide 10｜最佳实践：技术团队最该讲清楚什么

建议讲稿：

1. 一个很常见的误区是：以为 prompt 越长越好。其实真正重要的是任务表达是否清楚。
2. 最少要说清楚五件事：目标、范围、约束、验收标准、验证方式。
3. 另外，不要一开始就让 Agent 上来做大任务，先从边界清晰的小任务开始更稳。
4. Ask、Plan、Agent 最好形成组合，而不是用一种模式硬扛所有问题。
5. 最后一定要记住：生成结果不等于可以直接进生产，工程师仍然要保留审查权。

---

## Slide 11｜Harness Engineering：重点不是 magic prompt，而是 Agent 的运行环境

建议讲稿：

1. 到这里我们进入今天一个很关键的主题：Harness Engineering。
2. 很多人会把注意力放在“prompt 怎么写更厉害”，但真实团队里更重要的是 Agent 的运行环境设计。
3. 也就是说，不只是你怎么说，还包括：项目级规则怎么定义、角色边界怎么划分、高频任务怎么模板化、错误怎么自动暴露给 Agent。
4. 所以 Harness Engineering 的重点不是让 Agent 更神，而是让 Agent 更稳。
5. 这也是为什么企业落地时，环境设计往往比 prompt 调优更重要。

---

## Slide 12｜参考案例：为什么顶级团队更重视 Harness，而不是“神奇提示词”

建议讲稿：

1. 这不是我们自己总结出来的一套说法，而是行业里越来越明显的共识。
2. 比如 `github/awesome-copilot` 强调的是把 instructions、agents、hooks、workflows 做成可复用资产。
3. `walkinglabs/awesome-harness-engineering` 则把 harness 看成一整层系统设计，而不只是一个配置文件。
4. 这些参考都在说明：效果差很多时候不是模型不行，而是缺少结构、边界和反馈闭环。
5. 对企业来说，真正要买的是可预测、可治理、可回归的能力，而不是偶尔惊艳一次的演示效果。

---

## Slide 13｜Part 2：Live Demo、Harness Engineering 与动手实验

建议讲稿：

1. 接下来我们进入第二部分，把前面讲的能力真正落到一个统一场景里。
2. 这里我们会先做 Demo，再做实验，而且用同一个业务背景，减少大家来回切换上下文。
3. 重点是让大家看到：这些概念不是分散的，而是能组合成一条实际工作流。

---

## Slide 14｜Demo 场景：Customer Support Ticket Service

建议讲稿：

1. Demo 用的是一个很小的 ticket service，原因很简单：代码量小，便于现场理解，但又足够展示跨文件改动。
2. 我们要做的是一个典型的小增强：新增 `/tickets/summary`，并补上测试。
3. 这个场景很适合展示 Ask、Plan、Agent 的配合，也适合讲审批、测试验证和治理边界。
4. 大家可以把它理解成真实项目里最常见的一类任务：小功能增强。

---

## Slide 15｜Demo Prompt 建议

建议讲稿：

1. 这里给的是三段最典型的 prompt，不是为了背模板，而是为了看三种模式各自承担什么角色。
2. Ask 负责理解当前项目，Plan 负责把实现步骤说清楚，Agent 负责真正执行和验证。
3. 这里有一个很实用的习惯：把“run tests when finished”这种要求明确写进去，帮助 Agent 形成闭环。
4. 另外，如果现场发现任务太大，要及时缩小范围，而不是硬让 Agent 一把梭。

---

## Slide 16｜升级版 Hands-on Lab 设计

建议讲稿：

1. 这次实验不是只做一个简单任务，而是拆成三段：AI-DLC、Harness Engineering、Multi-Agent。
2. 第一段让大家体验完整开发生命周期；第二段让大家理解怎么设计 Agent 的运行环境；第三段让大家体验多角色协作。
3. 这三段放在一起，基本就能覆盖客户团队从“会用”到“会落地”的关键路径。
4. 所以实验的重点已经不只是 prompt，而是规则、角色、流程和验证闭环。

---

## Slide 17｜实验引导话术：学员要学会的不是“一个 prompt”

建议讲稿：

1. 做实验时，我建议反复提醒学员：你们学的不是一句 prompt，而是一套流程。
2. 先 Ask 理解，再 Plan 缩范围，再 Agent 执行，最后回到 review 和验证。
3. 只有把这套流程内化，大家才能把今天的练习迁移到真实项目里。
4. 如果只记住一个 prompt，回去很快就会失效；如果记住一条工作流，回去就能自己扩展。

---

## Slide 18｜落地建议：从 Workshop 到团队试点

建议讲稿：

1. workshop 结束后，真正关键的是怎么试点，而不是一次性铺开。
2. 我通常建议分三步：先选低风险、小范围、可测试的任务；再明确治理方式；最后沉淀团队模板。
3. 这三步对应的是 adoption 里最常见的三个问题：先做什么、谁来管、怎么复用。
4. 对技术团队来说，能不能和现有工程流程兼容，往往比模型本身更重要。

---

## Slide 19｜附录：交付清单

建议讲稿：

1. 这一页主要是帮助客户知道，今天 workshop 结束后，他们拿走的不是一份 PPT，而是一套可复用材料。
2. 包括 PPT、讲师脚本、实验手册，以及可直接运行的 lab starter。
3. 这也符合今天一直在讲的思路：把一次性的讲解，变成可复用的团队资产。

---

## Slide 20｜Q&A

建议讲稿：

1. 收尾时我建议不要只问“还有什么问题”，而是主动抛出三个引导问题。
2. 第一，你们最适合先从哪类任务试点 Agent？第二，你们当前更适合保守审批还是更高自治？第三，哪些任务其实仍然更适合 Ask 或 Plan？
3. 这样可以把讨论从“功能好不好用”转到“团队怎么落地”。
4. 如果客户开始讨论试点范围和治理方式，说明这场 workshop 已经进入真正有价值的阶段。

## 讲师使用建议（额外）

### 1. 语气建议
- 少讲“革命性”“颠覆性”
- 多讲“适用场景”“边界”“验证”“工程流程”
- 客户技术团队通常更买账“稳”和“可控”，而不是“炫”

### 2. 节奏建议
- 前半段讲框架，后半段讲实践
- 每讲完一个概念，都尽量落一句“这在真实项目中意味着什么”
- 避免连续 10 分钟抽象概念堆叠，穿插例子和过渡句

### 3. 一句总收口
可用于最终总结：

> GitHub Copilot 的价值，不只是帮团队少写一点代码，
> 而是帮助团队把一部分开发工作从“手工执行”升级成“可控的 Agent 工作流”。
> 真正决定落地成败的，不只是模型能力，更是你怎么设计它的工作环境。
